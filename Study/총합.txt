############################################################
AWS 기본 강의 1~13강 통합 핵심 정리
############################################################

목표
- AWS 교육을 다시 들을 때 처음 보는 서비스 이름이 거의 없도록 만들기
- 서비스를 단순 암기하지 않고 "클라우드 구조와 흐름"으로 이해하기
- 세부 수치보다 서비스의 역할, 연결 관계, 선택 기준을 우선 이해하기

전체 흐름
사용자
-> DNS와 글로벌 네트워크
-> VPC 내부 진입
-> Load Balancer
-> 컴퓨팅 서비스(EC2=컴퓨터)에서 애플리케이션 실행
-> 스토리지 또는 데이터베이스에 데이터 저장(EC2가 아님)
-> IAM과 암호화로 보호
-> CloudWatch와 CloudTrail로 모니터링·감사
-> Auto Scaling으로 확장
-> 비용과 규정 준수 관리
-> Well-Architected Framework로 전체 구조 평가

디네/뷔/로/앱/스디비/암2/클2/오스/비규/평
============================================================
1. 클라우드 컴퓨팅의 출발점
============================================================

■ 클라우드 컴퓨팅
인터넷을 통해 서버, 스토리지, 데이터베이스 같은 IT 리소스를 필요한 만큼 즉시 사용하는 방식

핵심 특징
- On-Demand: 필요할 때 바로 생성
- Pay-as-you-go: 사용한 만큼만 비용 지불
- **********Elastic************: 수요에 따라 확장·축소
- 빠른 배포: 물리 서버 구매 없이 즉시 사용

온프레미스
= 회사가 서버와 데이터센터를 직접 보유·관리

클라우드
= AWS의 인프라를 빌려 사용

하이브리드
= 온프레미스와 AWS를 함께 사용

대표 예시
쇼핑몰 방문자가 갑자기 증가
-> 온프레미스는 미리 서버를 구매해야 함
-> AWS는 필요한 만큼 EC2를 늘렸다가 방문자가 줄면 다시 감소

장점
- 초기 하드웨어 비용 감소
- 빠른 확장과 서비스 출시

단점
- 사용량과 설정을 관리하지 않으면 비용 증가 가능
- 데이터와 권한 설정은 사용자가 책임져야 함

------------------------------------------------------------
■ 클라이언트와 서버
클라이언트
= 서비스를 요청하는 사용자나 프로그램

서버
= 요청을 받아 처리하고 결과를 반환하는 시스템

흐름
클라이언트 -> 요청 -> 서버 -> 처리 -> 응답 -> 클라이언트

------------------------------------------------------------
■ 프로비저닝(Provisioning)
서버, 스토리지, 네트워크 같은 리소스를 생성하고 사용할 수 있게 준비하는 것

프로비저닝 해제
= 필요 없는 리소스를 삭제하거나 중지하는 것

============================================================
2. AWS 글로벌 인프라
============================================================

■ AWS 글로벌 구조
AWS Cloud
-> Region
-> VPC/Availability Zone
-> Subnet
-> EC2, Resource

------------------------------------------------------------
■ 리전(Region)
서울, 도쿄처럼 AWS 인프라가 존재하는 지리적 지역

리전 선택 기준
- 규정 준수: 데이터를 특정 국가에 저장해야 하는가?
- 사용자 근접성: 사용자와 가까워 지연 시간이 짧은가?
- 서비스 가용성: 필요한 AWS 서비스가 제공되는가?
- 비용: 리전별 요금 차이가 있는가?

------------------------------------------------------------
■ 가용 영역(AZ)
리전 내부에 존재하는 독립적인 데이터센터 그룹

특징
- 독립된 전력과 네트워크
- 하나의 리전에 여러 AZ 존재
- 장애가 다른 AZ로 확산되지 않도록 격리

------------------------------------------------------------
■ 고가용성(High Availability)
일부 장애가 발생해도 서비스를 계속 제공하는 능력

Multi-AZ
= 여러 AZ에 리소스를 분산해 AZ 장애에 대비

Multi-Region
= 여러 리전에 시스템을 구성해 리전 전체 장애에 대비

------------------------------------------------------------
■ 내결함성(Fault Tolerance)
일부 구성 요소가 고장 나도 시스템이 거의 중단 없이 정상 작동하는 능력

고가용성
= 장애 후 빠르게 다른 시스템으로 전환

내결함성
= 장애가 나도 서비스가 계속 작동하도록 더 강하게 이중화

------------------------------------------------------------
■ Edge Location
리전과 별도로 전 세계 곳곳에 위치한 캐시·네트워크 거점

대표 서비스
- Amazon CloudFront
- Route 53
- Global Accelerator

------------------------------------------------------------
■ Amazon Route 53
AWS의 DNS 서비스

역할
도메인 이름을 IP 주소나 AWS 리소스로 연결

예)
www.shop.com
-> Route 53
-> 가장 적절한 서버나 리전으로 연결

------------------------------------------------------------
■ Amazon CloudFront
사용자와 가까운 Edge Location에 콘텐츠를 캐시하는 CDN 서비스

적합한 데이터
예) 이미지, 동영상, CSS, JavaScript, 정적 웹 파일

흐름
사용자
-> 가까운 Edge Location
-> 캐시가 있으면 즉시 제공
-> 없으면 원본 서버에서 가져와 캐시 후 제공

장점
- 지연 시간 감소
- 원본 서버 부하 감소

------------------------------------------------------------
■ AWS Global Accelerator
AWS 글로벌 네트워크를 이용해 애플리케이션까지의 연결 경로 자체를 최적화

CloudFront
= 콘텐츠를 캐시해 빠르게 제공

Global Accelerator
= 네트워크 연결 경로 자체를 빠르고 안정적으로 제공

3. AWS 리소스를 관리하는 방법
============================================================

■ AWS Management Console
웹 브라우저에서 클릭으로 AWS를 관리

장점
- 초보자가 가장 이해하기 쉬움

단점
- 반복 작업과 대규모 관리에 비효율적

------------------------------------------------------------
■ AWS CLI
명령어로 AWS 서비스를 관리

장점
- 빠른 반복 작업
- 스크립트 자동화 가능

------------------------------------------------------------
■ AWS SDK
Python, Java 같은 애플리케이션 코드에서 AWS **API**를 호출하는 도구

예)
Python 애플리케이션
-> SDK 사용
-> S3에 파일 저장

------------------------------------------------------------
■ AWS CloudFormation
AWS의 코드형 인프라(IaC) 서비스

IaC(Infrastructure as Code)
= 서버, 네트워크, DB 같은 인프라를 **코드로 직접 짜고** 자동 생성

흐름
CloudFormation Template
-> VPC, EC2, RDS, S3 등을 자동 생성

장점
- 동일 환경 반복 생성
- 수동 설정 오류 감소
- 변경 이력 관리

관리 방법의 흐름
Console
-> CLI
-> SDK
-> CloudFormation

뒤로 갈수록 자동화와 반복 가능성이 높아짐

4. 네트워크의 핵심: VPC
============================================================

■ Amazon VPC
사용자가 AWS 안에 만드는 격리된 가상 네트워크

VPC 안에서 결정하는 것
- IP 주소 범위
- 서브넷
- 라우팅
- 인터넷 연결
- 보안 규칙

VPC
= 리전 범위

Subnet
= 하나의 AZ 범위

------------------------------------------------------------
■ CIDR
VPC와 서브넷이 사용할 IP 주소 범위를 표현하는 방식

예)
VPC: 10.0.0.0/16

Subnet A: 10.0.1.0/24
Subnet B: 10.0.2.0/24

------------------------------------------------------------
■ 서브넷(Subnet)
VPC의 IP 주소 범위를 나눈 네트워크 공간

Public Subnet
= 인터넷과 직접 통신해야 하는 리소스 배치

예) ALB, Public EC2, NAT Gateway

Private Subnet
= 인터넷에서 직접 접근하면 안 되는 리소스 배치

예) RDS, 내부 애플리케이션 서버

------------------------------------------------------------
■ Public Subnet의 조건
- VPC에 Internet Gateway 연결
- Route Table에 인터넷 경로 존재
- 해당 Route Table이 서브넷과 연결
- 리소스에 Public IP 존재

------------------------------------------------------------
■ Route Table
네트워크 트래픽을 어디로 보낼지 결정하는 경로표

구성
- Destination: 목적지
- Target: 보낼 대상

예)
0.0.0.0/0 -> Internet Gateway

------------------------------------------------------------
■ Internet Gateway(IGW)
VPC와 인터넷을 연결하는 게이트웨이

주의
IGW만 연결했다고 인터넷 통신이 되는 것은 아님
-> Route Table과 Public IP도 필요

------------------------------------------------------------
■ NAT Gateway
Private Subnet의 리소스가 인터넷으로 나갈 수 있게 하는 서비스

특징
- Private -> Internet 가능
- Internet -> Private 직접 접근 불가
- Public Subnet에 위치

대표 예시
Private Subnet의 EC2가 운영체제 업데이트 파일 다운로드

------------------------------------------------------------
■ Virtual Private Gateway(VGW)
Site-to-Site VPN을 통해 온프레미스와 VPC를 연결하는 VPC 측 출입구

------------------------------------------------------------
■ AWS Client VPN
개별 원격 사용자가 AWS 또는 회사 내부망에 안전하게 접속

대표 예시
재택근무 직원이 회사 VPC에 접속

------------------------------------------------------------
■ AWS Site-to-Site VPN
회사 네트워크와 AWS VPC를 인터넷 기반 암호화 터널로 연결

장점
- 비교적 빠르고 저렴하게 구축

단점
- 인터넷 품질에 영향을 받음

------------------------------------------------------------
■ AWS Direct Connect
회사와 AWS를 전용 회선으로 연결

장점
- 높은 대역폭
- 안정적
- 인터넷을 거치지 않음

단점
- 구축 비용과 시간이 큼

------------------------------------------------------------
■ AWS PrivateLink
인터넷을 거치지 않고 VPC에서 AWS 서비스나 다른 VPC의 특정 서비스에 비공개로 접근

핵심
전체 VPC를 연결하는 것이 아니라 "특정 서비스"를 비공개로 제공

------------------------------------------------------------
■ AWS Transit Gateway
여러 VPC와 온프레미스 네트워크를 중앙 허브 방식으로 연결

필요한 상황
VPC가 많아져 VPC Peering을 일일이 연결하기 어려울 때

5. 네트워크 보안
============================================================

■ Security Group
EC2 같은 리소스 단위의 가상 방화벽

특징
- Stateful
- Allow 규칙만 사용
- 기본 Inbound 거부
- 기본 Outbound 허용

Stateful
= 요청이 허용되면 그에 대한 응답은 자동 허용

------------------------------------------------------------
■ Network ACL(NACL)
서브넷 단위의 방화벽

특징
- Stateless
- Allow와 Deny 사용 가능
- Inbound와 Outbound를 각각 검사
- 규칙 번호 순서대로 평가

Stateless
= 요청과 응답을 각각 허용해야 함

------------------------------------------------------------
■ Security Group vs NACL

Security Group
- 대상: 개별 리소스
- 방식: Stateful
- 규칙: Allow만
- 용도: 주된 접근 제어

NACL
- 대상: 서브넷 전체
- 방식: Stateless
- 규칙: Allow + Deny
- 용도: 서브넷 수준 추가 보호

------------------------------------------------------------
■ 일반적인 인터넷 요청 흐름
사용자
-> Internet
-> Internet Gateway
-> NACL
-> Security Group
-> EC2

6. 컴퓨팅: 코드를 어디서 실행할 것인가
============================================================

■ Amazon EC2
AWS의 가상 서버 서비스

EC2
= 서비스 이름

EC2 Instance
= 실제로 생성한 가상 서버 1대

사용자가 관리하는 것
- 운영체제
- 애플리케이션
- 패치
- 보안 설정

장점
- 운영체제와 서버를 자유롭게 제어

단점
- 관리 부담이 큼

------------------------------------------------------------
■ AMI(Amazon Machine Image)
EC2 인스턴스를 생성하기 위한 템플릿

포함 가능
- 운영체제
- 소프트웨어
- 설정

예)
웹 서버가 설치된 AMI로 동일한 EC2를 여러 대 생성

------------------------------------------------------------
■ EC2 인스턴스 유형

범용
= CPU와 메모리 균형

컴퓨팅 최적화
= CPU 중심 작업

메모리 최적화
= 대용량 메모리 작업

가속 컴퓨팅
= GPU, AI, 그래픽

스토리지 최적화
= 높은 디스크 I/O

------------------------------------------------------------
■ Scale Up
서버 한 대의 CPU나 RAM을 증가

장점
- 구조가 단순

단점
- 확장 한계와 단일 장애점 존재

------------------------------------------------------------
■ Scale Out
서버 개수를 증가

장점
- 대규모 트래픽 대응
- 장애 분산

단점
- Load Balancer와 분산 구조 필요

------------------------------------------------------------
■ EC2 Auto Scaling
수요에 따라 EC2 인스턴스 수를 자동 증가·감소
-변경 사항에 바로 적용 or 예약해서

설정
- 최소 용량
- 원하는 용량
- 최대 용량

장점
- 트래픽 증가 대응
- 수요 감소 시 비용 절감

------------------------------------------------------------
■ Elastic Load Balancing(ELB)
여러 서버로 트래픽을 분산하는 서비스군
방법) round robin, least connection, ip연결상태에따라, 가까운 위치 등

주요 유형
- ALB: HTTP/HTTPS, 웹 애플리케이션
- NLB: TCP/UDP, 매우 높은 성능
- GWLB: 네트워크 보안 장비 연결

ALB(Application Load Balancer)
= ELB 서비스군에 포함되는 로드 밸런서 유형

대표 구조
사용자
-> ALB
-> 여러 EC2
-> Auto Scaling

------------------------------------------------------------
■ AWS Lambda
이벤트가 발생할 때 코드를 실행하는 서버리스 서비스

구성
- Function: 실행 코드
- Trigger: 실행 이벤트
- Runtime: Python, Node.js 등 실행 환경

대표 예시
S3에 이미지 업로드
-> Lambda 실행
-> 이미지 크기 자동 조정

장점
- 서버 관리 없음
- 자동 확장
- 실행한 만큼 과금

단점
- 실행 시간과 환경에 제한
- 장시간 서버 프로그램에는 부적합

------------------------------------------------------------
■ Serverless
사용자가 서버를 직접 생성·관리하지 않고 코드나 기능에 집중하는 방식

서버가 실제로 없는 것이 아니라
AWS가 서버 운영을 대신 관리

------------------------------------------------------------
■ 컨테이너(Container)
애플리케이션 코드, 라이브러리, 실행 환경을 하나로 패키징

장점
- 어디서나 동일하게 실행
- VM보다 가볍고 빠름

------------------------------------------------------------
■ Amazon ECR
컨테이너 이미지를 저장하는 레지스트리

------------------------------------------------------------
■ Amazon ECS
AWS 방식의 컨테이너 오케스트레이션 서비스

------------------------------------------------------------
■ Amazon EKS
Kubernetes 기반 컨테이너 오케스트레이션 서비스

------------------------------------------------------------
■ AWS Fargate
서버를 직접 관리하지 않고 ECS나 EKS 컨테이너를 실행하는 컴퓨팅 방식

전체 흐름
Docker Image 제작
-> ECR 저장
-> ECS 또는 EKS가 관리
-> EC2 또는 Fargate에서 실행

------------------------------------------------------------
■ AWS Elastic Beanstalk
애플리케이션 **코드**를 업로드하면 EC2, Load Balancer, Auto Scaling 등 **인프라 전체**를 자동 구성하는 배포 서비스

장점
- 웹 애플리케이션을 빠르게 배포

단점
- 세부 제어는 직접 구성보다 제한적

------------------------------------------------------------
■ AWS Batch
대량의 배치 계산 작업을 자동 예약·실행

대표 예시
수천 개의 유전체 파일 분석 작업

------------------------------------------------------------
■ Amazon Lightsail
초보자와 소규모 웹 서비스용 간단한 가상 서버 서비스

------------------------------------------------------------
■ AWS Outposts
AWS 장비와 서비스를 고객 데이터센터(온프레미스)에 설치

사용 상황
- 데이터가 반드시 온프레미스에 있어야 함
- 매우 낮은 지연 시간이 필요함

7. 애플리케이션 구조와 서비스 연결

모든 기능이 하나의 애플리케이션에 강하게 결합

장점
- 초기 개발이 단순

■ 마이크로서비스

8. 스토리지: 데이터를 어떤 형태로 저장할 것인가
============================================================

스토리지 3종류
- Block Storage: EC2옆에 붙는 하드디스크
- Object Storage: S3에 존재
- File Storage: 여러 EC2가 동시에 공유하는 파일 시스템

------------------------------------------------------------
■ #1. 블록 스토리지
데이터를 작은 블록 단위로 저장

특징
- 필요한 블록만 수정
- 낮은 지연 시간
- 운영체제와 데이터베이스에 적합

대표 서비스
- Amazon EBS
- EC2 Instance Store

------------------------------------------------------------
■ Amazon EBS(Elastic Block Storage)
EC2에 연결하는 영구 블록 스토리지

특징
- EC2와 독립적으로 존재
- EC2 중지 후에도 데이터 유지
- 볼륨 크기와 성능 조정
- 암호화 가능
- Snapshot 백업 가능

대표 예시
EC2 운영체제 디스크 또는 데이터베이스 디스크

장점
- 영구 저장
- 백업과 복구 가능

단점
- 일반적으로 특정 AZ 리소스
- **사용하지 않아도 생성된 볼륨 비용 발생** 가능

------------------------------------------------------------
■ EC2 Instance Store
EC2 호스트 서버에 직접 연결된 임시 로컬 스토리지

특징
- 매우 빠름
- EC2 중지·종료 시 데이터 손실 가능
- Cache, Buffer, Scratch 데이터에 적합

핵심
EBS = 영구
Instance Store = 임시

------------------------------------------------------------
■ EBS Snapshot
EBS 볼륨의 특정 시점 백업

특징
- 첫 Snapshot은 전체 기준 데이터
- 이후 변경된 블록만 저장하는 증분 백업
- 새 EBS 볼륨 생성 가능
- 다른 리전 복사 가능

------------------------------------------------------------
■ Amazon Data Lifecycle Manager(DLM)
EBS Snapshot용의 생성, 보관, 삭제를 자동화

------------------------------------------------------------
■ #2. 객체 스토리지
파일을 객체 단위로 저장

객체 구성
- Key
- Data
- Metadata

특징
- 거의 **무제한** 확장
- 대용량 **비정형** 데이터에 적합
- 파일 일부가 아닌 **전체 객체 단위** 처리

------------------------------------------------------------
■ Amazon S3
AWS의 대표적인 완전관리형 객체 스토리지

구조
Bucket
-> Object

Object
= 하나의 파일

Bucket
= Object를 담는 컨테이너

특징
- 거의 무제한
- 높은 내구성
- 자동 확장
- 기본 비공개
- 정적 웹사이트 호스팅 가능

대표 예시
이미지, 동영상, PDF, 로그, 백업 파일

------------------------------------------------------------
■ S3 Versioning
같은 객체의 이전 버전을 보관

장점
- 실수로 수정·삭제한 파일 복구

단점
- 버전이 쌓이면 비용 증가

------------------------------------------------------------
■ S3 Lifecycle
일정 시간이 지나면 객체를 다른 Storage Class로 변경하거나 삭제
-> 더 저렴한 비용을 위해

예)
생성 직후: S3 Standard(가장 빠름, 자주 사용하는 데이터)
-> 30일 후: S3 Standard-IA(자주 사용하지 않으며 저렴, 즉시 검색 가능)
-> 1년 후: S3 Glacier( 장기 보관, 매우 저렴,대신 꺼내는 데 시간이 걸림)
-> 보존 기간 종료 후 추가 영구 보존 or 삭제

------------------------------------------------------------
■ S3 Storage Class(저장소의 계층)

S3 Standard
= 자주 접근하는 일반 데이터

S3 Intelligent-Tiering
= 접근 패턴을 알 수 없을 때 자동 티어 이동

S3 Standard-IA
= 자주 접근하지 않지만 즉시 검색 필요

S3 One Zone-IA
= 한 AZ에 저장, 저렴하지만 복원력 낮음

S3 Glacier Instant Retrieval
= 드물게 접근하지만 즉시 검색

S3 Glacier Flexible Retrieval
= 몇 분~몇 시간 기다릴 수 있는 아카이브

S3 Glacier Deep Archive
= 가장 저렴한 장기 보관, 복원에 오래 걸림

핵심 선택 기준
접근 빈도 + 복원 속도 + 비용

------------------------------------------------------------
■ S3 보안

Bucket Policy
= S3 버킷 자체에 연결하는 리소스 기반 정책

IAM Policy
= 사용자나 역할이 S3에서 수행할 수 있는 작업 정의

Presigned URL
= 제한된 시간 동안 특정 객체 접근 허용

S3 Access Point
= 하나의 S3 버킷에 여러 개의 전용 출입구를 만들고,
  출입구마다 별도의 접근 정책을 설정하는 기능

------------------------------------------------------------
■ #3. 파일 스토리지
폴더와 디렉터리 구조를 사용하는 공유 파일 시스템
*****S3는 원래부터 거기 있고 EC2개별로 api형식으로 각각 불러오는거고
EFS는 공유폴더를 따로 만들어서 거기서 ec2가 같이 쓰는 구조!!!!*****

------------------------------------------------------------
■ Amazon EFS(Elastic File System)
**Linux용** 완전관리형 NFS 파일 시스템 <-여러 EC2가 같은 파일을 **공유**해야 할 때

특징
- **공유 폴더** 만들어 여러 EC2가 동시에 연결
- 자동 확장·축소
- 여러 AZ에서 사용 가능

대표 예시
여러 웹 서버가 같은 업로드 파일을 공유

장점
- 공유 접근
- 용량 자동 확장

단점
- EBS보다 비용이 높을 수 있음
- Linux/NFS 중심

------------------------------------------------------------
■ Amazon FSx
특정 파일 시스템을 완전관리형으로 제공 -> 리눅스가 아닌 **윈도우** 형 등에 사용할때

종류
- FSx for Windows File Server
- FSx for Lustre
- FSx for NetApp ONTAP
- FSx for OpenZFS

대표 선택
Windows 공유 폴더
-> FSx for Windows

고성능 컴퓨팅·ML
-> FSx for Lustre

------------------------------------------------------------
■ S3 vs EBS vs EFS

S3
= 객체 스토리지
= 이미지, 로그, 백업, 정적 웹사이트

EBS
= 블록 스토리지
= EC2 OS 디스크, DB 디스크

EFS
= 공유 파일 스토리지
= 여러 EC2가 같은 파일 사용

온프레미스(회사)와 AWS 스토리지를 연결해주는 하이브리드 스토리지 서비스

장점
- 별도 재해 복구 데이터센터 비용 감소
- 장애 시 빠른 복구

10. 데이터베이스: 데이터 구조에 맞게 선택
============================================================

■ 데이터베이스 선택 원칙
모든 데이터에 하나의 DB를 사용하는 것이 아니라
**데이터 구조와 접근 방식에 맞는 다양한 DB를 선택**

주요 종류
- 1. 관계형 DB
- 2. NoSQL DB
    - 2-3. 문서 DB
    - 2-4. 그래프 DB
- 5. 인 메모리 캐시

------------------------------------------------------------
1-1. 관계형 데이터베이스
**행과 열**로 구성된 테이블에 데이터를 저장하고 테이블 간 관계를 사용

특징
- SQL 사용
- 고정된 스키마
- JOIN과 트랜잭션에 적합

대표 예시
고객 테이블 + 주문 테이블
-> 고객 ID로 연결

------------------------------------------------------------
- Amazon RDS
관리형 관계형 데이터베이스 서비스

지원 엔진
- Aurora
- MySQL
- PostgreSQL
- MariaDB
- Oracle
- Microsoft SQL Server

AWS가 관리
- 하드웨어
- 백업
- 패치
- 모니터링
- 장애 조치

사용자가 관리
- 데이터 구조
- 계정과 권한
- 쿼리와 설정
- 보안 구성

------------------------------------------------------------
- RDS Multi-AZ
다른 AZ에 대기 DB를 두고 장애 시 자동 Failover

목적
= 고가용성

------------------------------------------------------------
- RDS Read Replica
읽기만 하는 DB를 하나 더 복사해서 읽기 요청을 분신해서 처리하는 기능

목적
= 읽기 성능 향상

Multi-AZ
= 장애 대비

Read Replica
= 읽기 성능 확장

------------------------------------------------------------
1-2. Amazon Aurora
AWS가 설계한 MySQL·PostgreSQL 상위 호환 고성능 관계형 DB

특징
- 자동 스토리지 확장
- 여러 AZ에 데이터 복제
- 높은 가용성
- 여러 Read Replica 지원

적합
대규모 웹, 게임, 실시간 서비스

------------------------------------------------------------
2. NoSQL
고정된 테이블 관계 대신 Key-Value나 Document 구조 사용

장점
- 유연한 스키마
- 대규모 확장
- 빠른 단순 조회

단점
- 복잡한 JOIN과 관계형 쿼리에 부적합

------------------------------------------------------------
- Amazon DynamoDB
완전관리형 서버리스 NoSQL 데이터베이스 서비스 제공

구조
Table
-> Item
-> Attribute

지원 형태
- Key-Value
- Document

특징
- 한 자릿수 **밀리초 수준 응답**
- 자동 확장
- 서버 관리 없음
- **항목마다 속성이 달라도 됨**

대표 예시
게임 사용자 상태, 장바구니, 모바일 앱 데이터

------------------------------------------------------------
- DynamoDB Global Tables
여러 리전에 DynamoDB 데이터를 복제

목적
- 글로벌 사용자에게 낮은 지연
- 리전 장애 대비

------------------------------------------------------------
- 2-3. Amazon DocumentDB(문서DB)
MongoDB 호환 문서 데이터베이스

적합
JSON 형태의 반정형 데이터

대표 예시
사용자 프로필, 상품 카탈로그, 콘텐츠 관리

------------------------------------------------------------
- 2-4. Amazon Neptune(그래프DB)
그래프 데이터베이스

적합
데이터 간 복잡한 연결과 관계 분석

대표 예시
소셜 네트워크, 사기 탐지, 추천 관계

------------------------------------------------------------

5. Amazon ElastiCache
RAM에 자주 사용하는 데이터를 저장하는 완전관리형 캐시

지원
- Redis OSS
- Valkey
- Memcached

흐름
애플리케이션
-> Cache 확인
-> Cache Hit: 바로 반환
-> Cache Miss: RDS 조회 후 Cache 저장

장점
- 응답 속도 향상
- DB 부하 감소

단점
- 원본 DB를 대체하지 않음
- 캐시 무효화 전략 필요

------------------------------------------------------------
■ AWS Backup
EBS, EFS, RDS, DynamoDB 등 여러 AWS 서비스의 백업을 중앙 관리

기능
- 일정 자동화
- 보존 정책
- 리전 간 복사
- 규정 준수 보고

11. AI/ML의 기본 흐름
============================================================

■ AI
인간과 유사한 지능적 작업을 수행하는 시스템의 넓은 분야

■ ML
데이터에서 패턴을 학습해 예측이나 결정을 수행하는 AI의 하위 분야

■ Deep Learning
인공 신경망을 사용하는 ML의 하위 분야

■ Generative AI
텍스트, 이미지, 음악 등 새로운 콘텐츠를 생성하는 AI

------------------------------------------------------------
■ ML의 기본 과정
데이터 수집
-> 데이터 정제
-> Training
-> Model
-> Inference
-> 예측 결과

Training
= 과거 데이터로 모델 학습

Inference
= 새 데이터를 모델에 넣어 예측

핵심
좋은 데이터가 없으면 좋은 모델도 만들기 어려움

------------------------------------------------------------
■ AWS AI/ML 3단계

1. AI Services
= 이미 훈련된 기능을 API로 사용

2. Amazon SageMaker AI
= 자체 ML 모델을 구축·훈련·배포

3. ML Framework & Infrastructure
= EC2, GPU, TensorFlow, PyTorch 등을 직접 사용

뒤로 갈수록
- 사용자 정의 증가
- 전문 지식과 관리 부담 증가

------------------------------------------------------------
■ 주요 사전 구축 AI 서비스

Amazon Comprehend
= 텍스트, 핵심 문구, 감정 분석

Amazon Polly
= Text -> Speech

Amazon Transcribe
= Speech -> Text

Amazon Translate
= 언어 번역

Amazon Rekognition
= 이미지·동영상 분석

Amazon Textract
= 문서, 표, 양식에서 텍스트 추출

Amazon Kendra
= 기업용 지능형 검색

Amazon Lex
= 대화형 챗봇

Amazon Personalize
= 개인화 추천

------------------------------------------------------------
■ Amazon SageMaker AI
ML 모델의 구축, 훈련, 배포, 모니터링을 지원하는 완전관리형 ML 서비스

------------------------------------------------------------
■ Foundation Model(FM)

------------------------------------------------------------
■ Amazon Bedrock
여러 회사의 Foundation Model을 공통 API로 사용하는 완전관리형 생성형 AI 서비스

적합
- 생성형 AI 애플리케이션
- 기업 데이터 연결
- 챗봇과 에이전트 구축

------------------------------------------------------------
■ Amazon Q

Amazon Q Business

12. 데이터 분석과 데이터 파이프라인
============================================================

■ 데이터 분석
과거 데이터를 정리하고 분석하여 인사이트와 추세를 찾는 과정

------------------------------------------------------------
■ ETL
Extract
-> Transform
-> Load

Extract
= 여러 소스에서 데이터 추출

Transform
= 정제·변환

Load
= 분석 시스템에 적재

ELT
= 먼저 저장한 뒤 필요할 때 변환

------------------------------------------------------------
■ 데이터 파이프라인
데이터의 수집, 저장, 변환, 분석 과정을 자동화한 흐름

전체 구조
Data Source: 데이터 생성되는 곳
-> Ingestion: 데이터 가져오기 Kafka
-> Storage: 데이터 저장 S3
-> Catalog: 데이터 위치 관리 Glue
-> Processing: 데이터 전처리 Glue, Spark
-> Query: 저장된 데이터 SQL로 조회 Athena
-> Visualization / ML: 분석 결과 활용 QuickSight/SageMaker

------------------------------------------------------------
■ Data Lake
원시 정형·비정형 데이터를 대규모로  **그대로** 저장

대표 서비스
Amazon S3

장점
- 유연함
- 다양한 분석에 재사용 가능

------------------------------------------------------------
■ Data Warehouse
분석하기 좋게 정제/가공된 데이터 저장소

대표 서비스
Amazon Redshift

장점
- 대규모 SQL 분석에 최적화

------------------------------------------------------------
■ Data Mart
업무 목적에 맞게 특정 부서만 사용하는 데이터 저장소

------------------------------------------------------------
■ Amazon Kinesis Data Streams
실시간 스트리밍 데이터를 수집+저장

대표 예시
주식 거래, 센서, 클릭 로그

------------------------------------------------------------
■ Amazon Data Firehose
스트리밍 데이터를 실시간으로 S3, Redshift 같은 목적지로만 전달

핵심
전달과 확장을 AWS가 관리

------------------------------------------------------------
■ AWS Glue Data Catalog
데이터의 위치와 구조를 기록, 관리하는 중앙 메타데이터 저장소

Metadata
= 데이터에 대한 정보

예)
파일 위치, 컬럼 이름, 데이터 타입

------------------------------------------------------------
■ AWS Glue
완전관리형 ETL 서비스

역할
- 데이터 검색
- 정제
- 변환
- 작업 예약

------------------------------------------------------------
■ Amazon EMR
Spark, Hadoop, Hive 기반 대규모 빅데이터 처리 서비스

적합
- 복잡한 대규모 처리
- 빅데이터 전문 인력이 있는 환경

------------------------------------------------------------
■ Amazon Athena
S3 데이터를 이동하지 않고 SQL로 직접 분석하는 서버리스 쿼리 서비스

장점
- 서버 관리 없음
- 실행한 쿼리 기준 과금

------------------------------------------------------------
■ Amazon Redshift
완전관리형 데이터 웨어하우스

적합
- 빈번한 대규모 분석
- 정형·반정형 데이터 SQL 분석

------------------------------------------------------------
■ Amazon QuickSight
AWS의 BI 대시보드와 시각화 서비스

------------------------------------------------------------
■ Amazon OpenSearch Service
로그, 검색, 운영 데이터의 실시간 검색·분석·시각화

------------------------------------------------------------
■ 대표 데이터 파이프라인 예시
DynamoDB
-> Kinesis Data Streams
-> Data Firehose
-> Lambda로 JSON을 CSV로 변환
-> S3 Data Lake
-> Glue Data Catalog
-> Athena로 분석
-> SageMaker AI로 모델 훈련

13. 보안의 기본 구조: 인증 및 권한 부여
============================================================

보안 흐름

-> 데이터 암호화
-> 모니터링
-> 위협 탐지
-> 조사와 대응

------------------------------------------------------------
■ 인증(Authentication)
사용자나 시스템이 누구인지 확인

질문
"당신은 누구인가?"

예)
아이디 + 비밀번호 + MFA

------------------------------------------------------------
■ 권한 부여(Authorization)
인증된 사용자가 무엇을 할 수 있는지 결정

질문
"무엇을 할 수 있는가?"

------------------------------------------------------------
■ AWS 공동 책임 모델

AWS
= Security of the Cloud
= 클라우드 자체의 보안

책임
- 데이터센터
- 물리 서버
- 네트워크 장비
- 가상화 계층
- 글로벌 인프라

고객
= Security in the Cloud
= 클라우드 안에서 사용하는 데이터와 설정의 보안

책임
- 데이터
- IAM
- Security Group
- NACL
- 암호화
- 애플리케이션 설정
- 필요한 경우 OS 패치

핵심
완전관리형 서비스라도 데이터와 접근 권한은 고객 책임

------------------------------------------------------------
■ AWS 계정 Root User
AWS 계정의 모든 권한을 가진 소유자

보안 원칙
- 강력한 비밀번호
- MFA 적용
- 일상 작업에 사용 금지
- Access Key 생성 지양

------------------------------------------------------------
■ AWS IAM
AWS의 인증과 권한을 관리하는 서비스

구성
- User
- Group
- Role
- Policy

기본 원칙
모든 작업은 기본 거부
-> 명시적으로 허용해야 가능

------------------------------------------------------------
■ IAM User
AWS 계정 안에서 개별 사람이나 프로그램에게 만들어주는 로그인 계정/장기 자격 증명

------------------------------------------------------------
■ IAM Group
여러 IAM 사용자를 묶어 동일한 권한을 적용

------------------------------------------------------------
■ IAM Role
일정 시간 동안 AWS서비스 및 사용자에게 주는 임시 권한 

사용 대상
- AWS 서비스
- 외부 사용자
- 다른 계정
- 애플리케이션

장점
고정 Access Key를 저장하지 않아도 됨

------------------------------------------------------------
■ IAM Policy
권한을 정의하는 JSON 문서

핵심 요소
- Effect: Allow 또는 Deny
- Action: 허용·거부할 API 작업
- Resource: 대상 리소스

정책 평가 핵심
- 기본 거부
- Allow가 있으면 허용
- 명시적 Deny가 있으면 항상 거부

------------------------------------------------------------
■ 최소 권한 원칙
업무에 필요한 권한만 부여

예)
보고서 담당자
-> 특정 S3 버킷의 Read 권한만 부여

------------------------------------------------------------
■ IAM Identity Center
여러 AWS 계정을 하나의 로그인으로 관리하는 서비스
한 번 로그인(Single Sign-On)으로 여러 AWS 계정에 접근가능

------------------------------------------------------------
■ AWS Secrets Manager
DB 비밀번호, API Key 같은 비밀 정보를 안전하게 저장/보관하는 금고

------------------------------------------------------------
■ AWS Systems Manager
EC2와 하이브리드 서버의 운영, 패치, 명령 실행, 인벤토리등 EC2를 원격으로 관리하는 서비스

SSL/**TLS**, **HTTPS**

------------------------------------------------------------
■ AWS Certificate Manager(ACM)
SSL/TLS 인증서를 생성·관리·배포

------------------------------------------------------------
■ Amazon Macie(메이시)
머신러닝을 이용해 S3의 개인정보와 민감 데이터를 탐지

17. 다중 계정과 거버넌스 : 조직 전체의 AWS 사용 규칙을 관리하는 것

중요
SCP가 권한을 직접 부여하는 것은 아님
-> **IAM(각 AWS 계정의 관리자가주는)이 권한을 허용하더라도 SCP가 막으면 실행 불가**

------------------------------------------------------------
■ Consolidated Billing

구성
Landing Zone
= 표준 다중 계정 환경

Account Factory
= 표준 계정 자동 생성

Guardrail / Control
= 보안·규정 준수 규칙

Dashboard
= 조직 상태 확인

------------------------------------------------------------
■ AWS Service Catalog
조직에서 허용한 AWS 리소스와 구성을 카탈로그(목록)로 제공

소프트웨어 라이선스(소프트웨어를 사용할 수 있는 사용 권한)를 관리하고 규정 위반을 방지

BYOL
= 기존 보유 라이선스를 AWS에서 사용

------------------------------------------------------------
■ AWS Health Dashboard
AWS가 내 계정과 리소스에 영향을 주는 AWS 장애, 유지보수, 변경 사항을 알려주는 서비스

------------------------------------------------------------
■ AWS Trusted Advisor
AWS 모범 사례(Best Practice)를 기준으로 내 AWS 환경을 검사하고 개선 사항을 추천하는 서비스

검사 영역
- 비용 최적화
- 성능
- 보안
- 내결함성
- 서비스 한도

------------------------------------------------------------
■ IAM Access Analyzer

-> 외부접근, 과도한 권한, 사용않는권한을 찾아줌

목적
= 최소 권한 달성

18. AWS 요금과 비용 관리
============================================================

■ AWS 요금의 3가지 원칙

1. 종량제
= 사용한 만큼 지불

2. 약정 할인
= 1년 또는 3년 사용을 약정해 할인

3. 사용량 할인
= 많이 사용할수록 단가 감소

------------------------------------------------------------
■ 비용의 3대 요소
- Compute: 컴퓨팅(서버실행)
- Storage
- Outbound Data Transfer: 외부로 나가는 데이터 전송 비용

Inbound
= 대부분 무료

Outbound
= 대부분 비용 발생

------------------------------------------------------------
■ EC2 요금 방식

On-Demand
= 약정 없이 사용
= 사용량이 불확실할 때

Savings Plans: 절약형

Dedicated Instance: 전용 인스턴스

20. 클라우드 마이그레이션
============================================================

■ 클라우드 마이그레이션
온프레미스 또는 다른 클라우드의 애플리케이션과 데이터를 AWS로 이전

3단계
1. Assess
2. Mobilize
3. Migrate & Modernize

------------------------------------------------------------
■ 1단계: Assess
현재 환경, 비용, 준비 상태, 비즈니스 가치를 분석

대표 서비스
Migration Evaluator

------------------------------------------------------------
■ 2단계: Mobilize
마이그레이션 계획을 구체화하고 서버·애플리케이션 의존성을 파악

대표 서비스
- Application Discovery Service
- Migration Hub

------------------------------------------------------------
■ 3단계: Migrate & Modernize
서버, 애플리케이션, DB, 데이터를 실제로 이전하고 개선

대표 서비스
- Application Migration Service
- AWS DMS
- DataSync
- Transfer Family
- Snowball Edge

------------------------------------------------------------
■ AWS Cloud Adoption Framework(CAF)
조직이 클라우드 전환을 준비하고 관리하도록 지원하는 프레임워크

6가지 관점
- Business
- People
- Governance
- Platform
- Security
- Operations

비즈니스 역량
= Business, People, Governance

기술 역량
= Platform, Security, Operations

------------------------------------------------------------
■ 마이그레이션 7R

1. Relocate
= 기존 VM·컨테이너의 호스팅 위치만 이동

2. Rehost
= 변경 없이 그대로 이전
= Lift and Shift

3. Replatform
= 핵심 코드는 유지하고 일부 클라우드 최적화
예) MySQL -> Amazon RDS

4. Refactor / Re-architect
= 클라우드에 맞게 애플리케이션을 재설계

5. Repurchase
= 기존 제품을 새로운 SaaS로 교체

6. Retain
= 당장은 기존 환경에 유지

7. Retire
= 더 이상 필요 없는 시스템 종료

변경 수준
Rehost < Replatform < Refactor

------------------------------------------------------------
■ Migration Evaluator
현재 IT 환경과 예상 AWS 비용을 분석해 마이그레이션 비즈니스 사례 작성

------------------------------------------------------------
■ AWS Application Migration Service
온프레미스 또는 다른 클라우드의 서버와 애플리케이션을 AWS로 이전

장점
- 복제 중 기존 서비스 운영 가능
- 가동 중단 최소화

21. 데이터베이스와 데이터 마이그레이션

다른 DB 엔진으로 이전

예)

■ AWS Database Migration Service(DMS)
데이터베이스 데이터를 이전하고 지속 복제

핵심
DMS = Data 이동

장점
- 원본 DB 운영 중 이전 가능

DB 스키마와 코드 객체를 다른 엔진 형식으로 변환

- Function
- Stored Procedure

핵심
SCT = Schema 변환

다른 엔진으로 이전

- 일정 예약
- 대역폭 제한

- 보고서

핵심
온라인 대용량 데이터 이동

■ AWS Transfer Family

대상
- Amazon S3
- Amazon EFS

------------------------------------------------------------
■ AWS Snowball Edge
물리적 디바이스를 이용한 오프라인 대용량 데이터 전송

사용 상황
- 인터넷 없음
- 대역폭 부족
- 페타바이트급 데이터
- 외딴 지역

DataSync
= 온라인 전송

Snowball Edge
= 오프라인 물리 전송

23. AWS Well-Architected Framework
============================================================

■ AWS Well-Architected Framework
클라우드 아키텍처를 AWS 모범 사례 기준으로 설계·평가하는 프레임워크

중요한 이유
클라우드는 한 번 구축하고 끝나는 것이 아니라
지속적으로 측정하고 개선해야 함

------------------------------------------------------------
■ 6가지 Pillar

1. Operational Excellence
= 운영, 자동화, 모니터링, 지속 개선

2. Security
= 최소 권한, 암호화, 데이터와 시스템 보호

3. Reliability
= 장애 복구, 자동 복구, 수요 변화 대응

4. Performance Efficiency
= 적절한 리소스와 기술을 효율적으로 사용

5. Cost Optimization
= 불필요한 비용 제거, 사용량과 크기 최적화

6. Sustainability
= 에너지 사용과 환경 영향을 최소화

------------------------------------------------------------
■ AWS Well-Architected Tool
6가지 Pillar 기준으로 워크로드를 평가하는 무료 도구

기능
- 질문 기반 아키텍처 검토
- 위험 영역 확인
- 개선 방법 추천
- 마일스톤 추적
- 사용자 지정 Lens

26. 반드시 기억할 비교
============================================================

EC2 vs Lambda
EC2
= 서버를 직접 관리
Lambda
= 코드만 실행, 서버 관리 없음

S3 vs EBS vs EFS
S3
= 객체
EBS
= EC2 디스크
EFS
= 공유 파일

RDS vs DynamoDB
RDS
= SQL, 관계, 고정 스키마
DynamoDB
= NoSQL, 유연한 스키마, 빠른 확장

Multi-AZ vs Read Replica
Multi-AZ
= 장애 대비
Read Replica
= 읽기 성능

Security Group vs NACL
Security Group
= 리소스, Stateful
NACL
= 서브넷, Stateless

CloudWatch vs CloudTrail
CloudWatch
= 시스템 상태
CloudTrail
= 누가 무엇을 했는지

Inspector vs GuardDuty vs Detective
Inspector
= 취약점 검사
GuardDuty
= 위협 탐지
Detective
= 원인 조사

Config vs Audit Manager
Config
= 구성 규칙 준수
Audit Manager
= 감사 증거 수집

Route 53 vs CloudFront
Route 53
= 목적지 찾기
CloudFront
= 가까운 곳에서 콘텐츠 제공

VPN vs Direct Connect
VPN
= 인터넷 기반 암호화
Direct Connect
= 전용 회선

DataSync vs Transfer Family vs Snowball
DataSync
= 대용량 온라인 데이터 이동
Transfer Family
= FTP/SFTP/FTPS 파일 전송
Snowball
= 오프라인 물리 전송

DMS vs SCT
DMS
= 데이터 이동
SCT
= 스키마 변환

27. AWS 전체를 한 문장 흐름으로 이해하기
============================================================

사용자가 Route 53을 통해 서비스 주소를 찾고
-> CloudFront가 가까운 Edge Location에서 콘텐츠를 제공하며
-> 트래픽은 VPC의 Public Subnet에 있는 ALB로 들어가고
-> Security Group과 NACL을 통과한 뒤
-> Auto Scaling으로 관리되는 EC2, 컨테이너 또는 Lambda가 요청을 처리하고
-> 데이터는 S3, EBS, EFS, RDS, DynamoDB 등에 저장되며
-> IAM과 KMS가 접근 권한과 암호화를 관리하고
-> CloudWatch가 성능을 모니터링하고
-> CloudTrail이 API 활동을 기록하며
-> GuardDuty와 Security Hub가 보안 위협을 탐지하고
-> Organizations와 Control Tower가 여러 계정을 통제하고
-> Budgets와 Cost Explorer가 비용을 관리하며
-> Well-Architected Framework가 전체 아키텍처를 지속적으로 평가하고 개선한다.
