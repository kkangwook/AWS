--------------------------[네트워크 캡슐화(Encapsulation)]---------------------------
1. 보내려는 데이터
- 예: HTML 문서
- Payload(페이로드): 해당 계층에서 전달하려는 실제 내용

2. 캡슐화란?
- 데이터를 보내면서 각 계층에 필요한 제어 정보를 덧붙여 감싸는 과정.
- 아래는 TCP 기반 HTTPS 통신을 단순화한 예시.

HTML
→ HTTP [ HTML ]
→ TLS [ HTTP [ HTML ] ]
→ TCP [ TLS [ HTTP [ HTML ] ] ]
→ IP [ TCP [ TLS [ HTTP [ HTML ] ] ] ]
→ Ethernet [ IP [ TCP [ TLS [ HTTP [ HTML ] ] ] ] ]

3. 단계별 역할
- HTTP: HTML 등의 데이터를 전달하기 위한 요청·응답 형식 제공
- TLS: HTTP 데이터를 암호화하고 무결성 보호
- TCP: 포트 번호로 서비스를 구분하고 신뢰성 있는 데이터 전달
- IP: 출발지·목적지 IP 주소를 이용해 네트워크 간 전달
- Ethernet: 같은 링크에서 MAC 주소를 이용해 프레임 전달

4. 수신 측: 역캡슐화(Decapsulation)
- 각 계층의 정보를 확인하고 처리하면서 내부 데이터를 위 계층으로 전달.
- TLS 단계에서는 암호화된 데이터를 복호화함.

Ethernet → IP → TCP → TLS → HTTP → HTML
--------------------------------------------------------------------------------------------
proxy(server): 클라이언트와 서버 사이에서 요청과 응답을 대신 전달하는 중계자
		cloudfront처럼 캐싱저장역할 -> 이런 역할은 현재에는 잘 안쓰임
reverse-proxy: 서버대신에 사람들의 요청을 받아서 분산처리 <- 얘는 많이 쓰임
			nginx또한 이 역할도 함

Nginx가 하는 역할
단순 웹서버뿐 아니라 (정적 파일 Serving)
- Reverse Proxy
- HTTP Load Balancing
- TLS Termination
- Caching
- Rate Limiting / Connection Limiting
- Access / Error Logging

-sticky session: 로드밸러서에 바뀌는 세션을 누가누구인지 달라붙어 알게해주는 애

--------------nginx의 설정 파일 ---------------------
/etc/nginx/sites-available/default
→ 실제 사이트 설정 파일을 보관하는 폴더.
→ 설정을 수정할 때는 여기의 파일을 고침.

/etc/nginx/sites-enabled/default        ->이거 나중에 sesac으로 바꿀꺼임
→ 활성화할 설정의 심볼릭 링크를 두는 폴더.
→ Nginx는 이 링크를 통해 available의 실제 설정을 읽음.

두 폴더로 나누는 이유:
→ 원본 설정을 보관하면서 링크 생성·삭제로 사이트를 활성화·비활성화하려고.

설정 수정: sudo vi /etc/nginx/sites-available/default
활성화: sudo ln -s /etc/nginx/sites-available/sesac /etc/nginx/sites-enabled/sesac   # 뒤에 만들 새로운 설정파일
비활성화: sudo unlink /etc/nginx/sites-enabled/sesac
수정 후 적용: sudo nginx -t && sudo systemctl reload nginx

※ enabled가 심볼릭 링크라면 그쪽을 편집해도 같은 원본이 수정됨.
